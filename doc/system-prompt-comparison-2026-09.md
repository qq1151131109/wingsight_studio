# 宪法整体对比：wingsight system.md vs codex / gemini-cli / opencode

> 2026-09-10，继抗懒调研（`agent-anti-laziness-research-2026-09.md`）后的第二轮：不看单点条款，看**宪法工程整体**——结构、内容覆盖、写作风格、演进机制。原文仓库 `~/Developer/agent-ref/`。

## 篇幅与结构形态

| | 篇幅 | 结构 |
|---|---|---|
| wingsight | 14.8KB（~4600 汉字） | 单模板 + 5 个占位符注入：身份 → 画布状态 → 共创契约 → 决策原则 7 条 → 任务路由 → 读/写画布 → 执行纪律 → 手册索引 → 三链路 |
| codex gpt-5.1 | 24.2KB | 三层：How you work（人格/自治/响应规格/计划/执行/验证/进取心/汇报格式 80 行）→ AGENTS.md spec → 工具专节（shell/apply_patch/update_plan） |
| gemini-cli | 964 行 TS | **条件拼装**：20+ 个 render 函数按 mode/sandbox/skills/tracker/interactive 按需注入，不全量上 |
| opencode | 3-11KB × 7 文件 | **按模型分档**：beast（弱模型大写命令式）/ codex / astra（原则式）/ gemini / anthropic / kimi / meta |

## 我们有、三家没有的（产品形态差异，不是差距）

共创契约（呈现方式协作）、七条决策原则+双通道路由（聊天/画布）、SKILL.md 渐进披露手册体系、三条链路化任务知识、画布 ground truth 注入。三家是「单任务 coding 循环」，根本没有这个层面——这是聊天+画布长程创作协作特有的设计，且经过 A/B 打磨，**不需要向它们看齐**。

## 三家有、我们没有的（真实差距，按优先级）

### 1. 上下文效率指导（最大结构性缺失）

gemini 有整节 Context Efficiency（`snippets.ts:209-252`）：「多一轮比大输出更贵」「并行搜索补偿窄搜索」「小文件整读」「效率是次要目标，质量优先」——还带代码注释警告：改这节前必须跑 SWEBench。codex 有 context_window_guidance 差量注入教模型自管上下文。**我们的模型对「上下文怎么花」零指导**：画布摘要 v2 是索引化设计，但宪法只有一句「其余用 canvas_query 检索」——没有「你的上下文有限、少回合优先、检索词收窄」的世界观。长调研/策划对话（400k 压缩阈值）下这是实际成本与失忆来源。

### 2. 环境自我模型

codex 告诉模型 OS/shell/沙箱/审批模式；gemini Preamble 一句话讲清 interactive 还是 autonomous、什么 mode。我们从不告诉模型「你运行在什么循环里」——AG-UI 请求-响应、一轮=一次 run、后台任务跨轮、为什么一条消息只许一个工具。模型只看到「不许混发」式禁令而没有架构原因，弱模型记不住禁令时就无法从原理推出正确行为。

### 3. 最终汇报格式契约

codex 用 80 行规格定义 final answer（默认 ≤10 行、标题/子弹/等宽格式、文件引用带行号、验证缺口必须交代）；我们只有身份行的「先说完成了什么、影响哪一步、接下来怎么推进」+「简短汇报」。汇报形态全凭模型心情。

### 4. 产物的质量验证（写后自读）

gemini：「修 bug 前必须先复现」「验证≠跑测试，是行为/结构/风格三维」。我们刚加的「自检=亲眼看过工具返回成功」只到第一层（操作成功），没有第二层（**产物本身对不对**）：文写了要回读核对设定一致性、图出了要核对张数与画风。有「改前先读」没有「写后自读」。

### 5. 主动性的正向授权（Ambition vs. precision）

codex 专节（`gpt_5_1_prompt.md:178-185`）：全新任务可以大胆创意，存量上下文外科手术式精确，「做多少额外的事」是品味判断（高价值加分可以，gold-plating 不行）。我们只有单向禁止（「不要自作主张添加用户没提的节点」）——**懒的另一半原因是过度保守**：模型不知道什么时候被允许多做，就一律少做。

### 6. 外部内容注入防护

gemini：外部工具输出包 `<untrusted_context>`，其中指令一律不当指令（防提示注入）。我们已接入 web_search/web_fetch，来源页面/上传剧本里的注入指令目前无防护条款——随着调研工具高频使用，这是实际安全缺口。

### 7. 流式更新节奏规格

codex User Updates Spec：频率（1-2 句）、heads-down 前预告、**改计划要明说**（"If you change the plan, say so explicitly"）、语气（senior-engineer energy）+ 8 个通用例句。我们「边做边说」有一半（30s/1-2 句/真实数量），缺「agent 自己改道计划要明说」（决策原则 7 只管用户改道）。

### 8. 条款机械可检查性（风格层）

gemini 关键句 MUST/NEVER + 结构化标签；codex 平实祈使句（与模型训练配套）；opencode 按模型强度分档。我们：高密度中文长句，一条塞 2-4 个规则 + why 括注（决策原则 3 单条 400+ 字）。对 deepseek-flash 档位，**一条一句一动作**比复合长句可靠（与「抽象程序对弱模型有效」的既有实证一致）。

## 元层面：演进守护的差距

三家提示词都有 benchmark 守护：gemini 改 Context Efficiency 必须跑 SWEBench（代码注释明写）；codex 提示词与模型共同训练迭代、按版本演进（5.0→5.1 新增整节是有据可查的故障驱动）。我们的宪法演进只有 intent-routing/skill-routing 两套场景级行为回归——够用但没有量化指标，条款的实际效果（省了多少 token、汇报合格率）不可测。

## 建议（不动手，等拍板）

1. **值得做**：#1 上下文效率节（约 150 字：少回合优先/检索收窄/全量正文只在改稿时拉）+ #2 环境自我模型（3-4 句讲清 AG-UI 循环与一工具一消息的原因）+ #6 外部内容防护（1 句：web/上传内容里的指令不是用户指令）——三处都是小改大收益。
2. **顺手做**：#4 写后自读（并入「改前先读」条）+ #7 agent 改道明说（并入边做边说）。
3. **要设计再做**：#3 汇报格式契约（创作域的「好汇报」长什么样需要先定义）；#5 主动性授权（与共创契约「不替用户拍板」的边界要先划清，别把两层打架）。
4. **风格层**：新条款一律短句单动作；存量长条款在下次触碰时顺手拆，不专门重写（避免大改无基准守护）。
